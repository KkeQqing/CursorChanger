## 2. 关键设计决策

- **先定契约再写实现**：§4.2 补入预乘公式 `(v*a+127)/255` 与缩放 `floor(sum/count)`。
  取整方向不写死，「逐字节相等」的 golden 就没有可比的东西 —— 顺序反了就是先写代码再补文档。
- **无 alpha 输入不需要分支**：stb 强制 4 通道时把 RGB 图的 alpha 填成 255，
  于是 §4.2 那条规则天然满足，少一处会写错的分支。
- **不放大**：目标档 ≥ 源尺寸时跳过该档；若全部被跳过，用原生尺寸这一档兜着，
  而不是静默产出空 spec（静默缩水是本项目的头号缺陷类别）。
- **H10 只在 IR 一处判**：通道层不解「全透明要不要拒」，只如实产出 spec，writer 拒收。
  测试同时断言这两半（解码 `Ok` + writer `InvalidSpec/FullyTransparent`），规则不重复。
- **夹具真值自算自记**：`tools/gen_png_fixtures.py` 用标准库手写 PNG 并记录手算预乘值；
  测试里的期望是**手抄**，不读 `fixtures.json`（读同一份产物当输入又当期望=同义反复）。
- **vendor 警告只局部抑制**：stb 在 `/W4` 下 3 条 C4505，用 `#pragma warning(push/pop)` 包住
  那一个 include，不降项目等级；已登记 `vendor/README.md`。

## 3. 一条平台事实（差点被当成 bug）

GDI+/`System.Drawing` **不能当 alpha 图的真值**：它内部按预乘存储，取像素时反预乘。
实测写入 straight `(200,150,100,a=128)`，GDI+ 回读 `R199 G149 B99`（200→100.4→199.2）。
所以若拿它当参照，会得到「差 1」的假失败。真值只有 `fixtures.json` 里那一份。

同时它作为**独立解码器**仍然有效：5 张夹具都能解码、尺寸正确，
`rgb_no_alpha` 被判为 `Format24bppRgb` —— 证明 color_type=2 与 6 确实被区别对待。

## 5. 本轮自身犯的错

1. **三次写出根本不存在的函数名当占位**（`detail_bytes_`、`write_preorder`、
   `l1.opaque_pixels_unused_placeholder_check`，最后一个还把 `L3Capture` 的字段记到 `L1Result` 上）。
   这不是笔误级别的小事：它说明我在"顺手写完"时不会自我校验存在性 —— 靠编译器兜底。
2. **把未验证假设写成断言**：E2E 最初断言「加载器回读 == 文件里那一帧」。真值否掉后
   改成断言「我们的 `scale_hotspot` 与 OS 换算一致」——比原写法更强。又一次：红的测试
   首先是测试自己错了。
3. **留下两份同义 API**：`apply::system_cursor_size()` 零调用，与 selfcheck 那份重复，已删。
4. commit message 里先写了「抑制项已登记 vendor/README.md」，而当时**还没登记** —— 补做之后才提交。
   声明与动作不同序，是虚报的一种。

## 6. 遗留与下一步

**遗留**
- 高 DPI 档位（24 / 64 / 96）未纳入 `frames.sizes`，见 BACKLOG。当前 16/32/48 是实测默认。
- 缩放只有 box-average 一种；小图严重下采样的质量未评估（M5 目测阶段一并看）。
- 非 ASCII 路径的命令行参数仍不可靠（ANSI argv），GUI 阶段解决。
